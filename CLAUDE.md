## Next.js version note

This project pins `next@16.3.1`, which is newer than most training data and has breaking changes vs. the Next.js you may know. Per `AGENTS.md`, consult `node_modules/next/dist/docs/` before writing App Router code — e.g. `01-app/02-guides/view-transitions.md` and `01-app/02-guides/upgrading/version-16.md` are directly relevant here (the codebase uses `ViewTransition` from React and the `LayoutProps<"/">` generated type in `app/layout.tsx`).

## Architecture

This is a single-page portfolio/gallery site with one real route plus one orphaned route:

- **`app/page.tsx`** is a thin Server Component: it reads `data/projects.ts`, runs `lib/discover-images.ts` against `public/work/<slug>/` to attach each project's real supporting-media list, and passes the result to **`components/PortfolioGallery.tsx`** — the actual live client component with all grid/overlay/interaction logic (description + supporting-media carousel positioned relative to the clicked tile's `DOMRect`, expanding down/right or up/left depending on which quadrant of the viewport the tile is in). Selecting a project pushes `/work/<slug>` via `window.history.pushState` and reads it back on `popstate` — there is no server-side routing for project detail views; everything happens client-side on `/`. See "Confirmed interaction model" below for the current (as of 2026-08-16) two-state shape.
- **`data/projects.ts`** is the single source of truth for content: an array of `Project` objects (`id`, `slug`, `title`, `categories`, `cover`, optional `description`/`images`). Category filter pills on the homepage are derived from this array (`Array.from(new Set(projects.flatMap(p => p.categories)))`). Many entries are commented out — that's the mechanism for hiding a project without deleting its data; `create-folders.sh` lists every project slug (including hidden ones) and creates its `public/work/<slug>/` image folder.
- **`app/work/[slug]/page.tsx`** exists as a route but its current contents are a near-duplicate of the homepage grid (it never reads `params`). It is not the detail view — don't assume this file renders project details; check `app/page.tsx`'s overlay logic instead. Its intended long-term role (direct-link/hard-refresh fallback vs. something else) is an open decision — do not delete or rebuild it without explicit approval.
- **`components/GridTile.tsx`, `components/ProjectOverlay.tsx`, `components/ProjectDetail.tsx`, `components/canvas-types.ts`** are **not imported by any route** — `app/page.tsx` reimplements grid+overlay logic inline instead. They're most likely unfinished work toward the `focused` interaction state (they contain the `Mode`/`Rect` types and the Motion `layoutId` shared-element-hero logic that the live route is missing), not a separate/rejected design. Treat as dead code unless a task specifically asks to wire them in; don't assume editing them affects the live site.
- **Images (and video) live under `public/work/<slug>/` as flat numbered files** (`01.jpg`, `02.png`, `010.mp4`, ...) — fully auto-discovered by `lib/discover-images.ts` (matches `/^(\d+)\.(jpe?g|png|mp4)$/i`, sorted numerically, cover excluded from the rest) at request time in `app/page.tsx`. There is no manual per-project image list anywhere in the codebase anymore (the old `images?: string[]` field on `Project` is unused dead weight, kept only because the orphaned dead components still reference it) — **just add/rename/remove files in the folder and the site picks it up automatically, no code or data changes needed.** Confirmed working live mid-session multiple times as the user actively added new numbered files (including videos) to existing project folders.
- Styling is Tailwind v4 (via `@tailwindcss/postcss`, `@theme inline` in `app/globals.css`) with a minimal light/dark palette; components use small hand-rolled Motion (`motion/react`) variants for fades/stagger rather than a shared animation utility.

## Design constraints (durable — confirmed decisions from prior sessions)

- **Stack:** Next.js App Router, Tailwind, and the existing `motion` package's established import pattern. Do not add `framer-motion` as a second dependency.
- **Aesthetic:** minimal, whitespace-driven, editorial — referencing high-end fashion/creative-studio portfolio sites (Renell Medrano's site was the specific reference for the ticked-ruler header and numbered index grid). Small, restrained thumbnails with generous surrounding space is the point; anything that makes images bigger or busier is moving away from the brief.
- **Ruler/header:** the ruler is a plain CSS `repeating-linear-gradient` tick bar (`components/Ruler.tsx`), not SVG. Header row is name / category-nav-or-back-link / "Information", full-width, outside the centered content frame. Must remain unchanged. The wrapping div (ruler + header row together) is `sticky top-0 z-30 bg-transparent` (added 2026-08-16, once the grid became tall enough to scroll) — deliberately transparent, not opaque: the user explicitly wants scrolling project thumbnails visible through the header/ruler area as they pass underneath it, not hidden behind a solid bar. `z-30` keeps the header/nav links clickable above the `z-20` project overlays regardless. Applies at all breakpoints, not just desktop.
- **Grid target spec (current, as of 2026-08-16 — implemented in `components/PortfolioGallery.tsx`, desktop/`lg:` only):** centered frame (`width: min(68vw, 1280px); max-width: calc(100vw - 48px)`), exactly 4 columns at their natural (untouched) track width — don't hardcode a column width, whatever the existing `grid-cols-4` + `gap-x-16` + frame width produce is correct by definition. Rows are a **fixed 300px each** (`grid-template-rows: repeat(rows, 300px)`, zero row gap — the 300px figure *is* the full row-to-row spacing, not a track height plus a separate gap) — this replaced an earlier "shrink rows to exactly fill the viewport height" model; the grid can now be taller than one viewport and the page scrolls for additional rows (~3 rows visible at a 1024px-tall viewport, matching the reference design). Each project's 300px-tall cell is "large and invisible" — the visible content (number + thumbnail) only occupies its top portion, the rest is intentional whitespace, not a bug. Within a cell: the **number is absolutely positioned at the cell's own top-left corner** (`lg:absolute lg:left-0 lg:top-0` on the cell itself, which is `lg:relative`) — not the thumbnail's corner, not centered with it. The **thumbnail is horizontally centered in the cell independently** (`lg:left-1/2 lg:-translate-x-1/2`) and sits **~25–30px below the number** (`lg:top-[42px]`, tuned for the number's own ~15px rendered height). These are two independently-positioned elements, not a centered stack sharing one wrapper — don't reintroduce a shared flex/absolute wrapper that centers both together, that was tried and explicitly rejected. Thumbnails render at their **natural aspect ratio** (`clamp(110px, 10vw, 180px)` as of 2026-08-17 — 2x the original `clamp(55px, 5vw, 90px)`; briefly passed through a 1.5x `clamp(83px, 7.5vw, 135px)` step first before the user asked to go to 2x off the *original* base, not 2x off the 1.5x value — same size whether the project is selected or not — see "Confirmed interaction model" below — no `object-cover`, no forced 3:4, no grey placeholder box). The expanded-state gallery carousel's image height is tied directly to this same clamp (via `anchorRect.height`, the cover's real measured size), so it scales automatically with any future change here — no separate carousel-specific size to keep in sync. Mobile/tablet (below `lg:`) are a completely separate, untouched layout (number stacked in normal block flow above the thumbnail, 8px gap, no absolute positioning) — any future edit to the desktop cell model must stay inside `lg:`-prefixed classes only.
- **Category filtering:** non-matching projects fade to `opacity: 0` with pointer-events disabled; they are never removed from the DOM/layout, and positions/numbers must never reflow on filter change. This part is already correctly implemented in `app/page.tsx`.
- **Confirmed interaction model (current, as of 2026-08-16 — two states, not three):** overview → open (click a project). Clicking a project reveals, and *permanently keeps on screen for as long as that project is open*: the cover (pixel-identical to its grid position/size, no resize), the description (below/above the cover), and a horizontal carousel of supporting media (beside the cover) — all positioned off `anchorRect`, the cover's rect captured once at click time (nothing about the cover ever changes afterward, so no re-measurement is ever needed). Clicking the cover *or* any carousel item shows that item enlarged as an additional element positioned below the carousel (or above, mirroring quadrant — same direction-mirroring logic as the description) — clicking a different item swaps the enlarged image in place; **the carousel itself never moves, hides, or rebuilds when you do this.** There is no third "focused" step, no vertical sidebar, and no shared-element `layoutId` morph between a thumbnail and the enlarged image anymore (see history note below) — the enlarged image is just a plain `motion.img`/`motion.video` keyed by its own `src`, faded in/out via `AnimatePresence` + the shared `fadeIn` variant, nothing more elaborate. Closing (Escape, clicking outside, or the header's "← Overview" link) always goes directly back to overview in one step — there is no intermediate "un-focus but stay open" state to step back through. `history.pushState` to `/work/[slug]` on open is for shareability/back-forward support, not a real route navigation for the click path.
- **Information overlay (added 2026-08-16):** the header's "Information" text is now a real toggle button, not decorative. Opens a full-viewport (`fixed inset-0`) panel, same `fadeIn`/`AnimatePresence` pattern as everything else, `z-20` (below the header's `z-30` so "← Overview" stays clickable above it). Content is deliberately set in `font-mono` (Tailwind's `font-mono` → `--font-geist-mono`, from the `Geist_Mono` already loaded in `app/layout.tsx` — this was the *first* thing in the codebase to actually use that font; before this it was loaded but dead weight) for a "typewriter resume" feel the user asked for by reference (a well-known minimal Alexander McQueen resume layout — single column, moderate density, generous `leading-loose` spacing), not by a design file they could share (hit a platform image-size limit — see Known Gotchas). All content in it is placeholder, same `[Placeholder — swap for your own words.]` convention as project descriptions — don't invent real contact info/clients/skills. Mutually exclusive with an open project (opening one closes the other, including the URL reverting to `/`). **Gotcha already hit once:** the panel being genuinely full-viewport means `onClick={stopPropagation}` on the *outer* wrapping div would eat every click in the viewport, breaking click-away-to-close entirely (there's no "outside" left to click) — the stopPropagation has to live on the inner content block only, so clicking the surrounding empty space still bubbles up to `<main>`'s close handler.
  - **History — this model went through two prior shapes the same day, don't reintroduce either without being asked:**
    1. **Cover grow-on-click** (briefly tried, then reverted): the cover grew ~30% on click instead of staying pixel-identical. Went through several real, separately-fixed bugs (a Motion ref-timing issue, `layoutId` not animating a persisting element's own resize, stale-mid-transition measurements affecting first the gallery's height then its position) before being fully reverted at the user's request ("maybe not scale it up, and keep it that size"). The relevant gotchas are preserved below since they're still true facts about Motion, even though nothing in the current code exercises them anymore.
    2. **Three-state model with a vertical sidebar** (superseded, not "buggy" — just replaced by a simpler design): overview → expanded (carousel appears, but hides once you focus something) → focused (a *different* layout appears elsewhere: big hero image + small vertical thumbnail rail, connected to the carousel/cover via a shared Motion `layoutId` FLIP animation). This worked and was fixed through many rounds (blank-until-second-click, viewport clipping on tight-space tiles, sidebar image stretching, etc.) but the user found the transition itself — the whole layout relocating and rebuilding when you click to focus — to be "too many steps" and asked for the current, simpler always-visible-carousel model instead. If a hero+sidebar-style view is ever wanted again, it's a real redesign to plan, not a quick revert.
- **No invented project descriptions/content.** Several projects intentionally have no description yet; don't fill them in speculatively. Edit `data/projects.ts` narrowly for a specific reason — don't reformat or reorder wholesale.

## Known gotchas

- **This isn't about the code, but matters for working in this repo: in a long session with many prior screenshots/images already in the conversation, the image-viewing tool can start rejecting *every* image — including ones just generated fresh (e.g. a brand-new Playwright screenshot) — with a "many-image requests: 2000 pixels" error, regardless of the new image's actual size.** Confirmed by direct testing: downsizing a rejected image to 647×900 (nowhere near 2000px on either axis) still failed identically. This is a cumulative/session-wide limit, not a per-image one — once it starts happening, further resizing attempts are wasted effort. Fall back to: (a) precise DOM/computed-style assertions via Playwright instead of eyeballing screenshots (this whole session's verification approach already leaned on this, so it degrades gracefully), or (b) asking the user to describe a reference image in words / answer targeted questions about it, if it's their reference material and not something regeneratable.
- **Extension mismatches are silent.** `.jpg` in `data/projects.ts` vs. an actual `.png`/`.jpeg` file produces a broken image with no build/type error. Always verify the real file extension.
- **Turbopack can lose track of new files.** Adding/moving files mid-session can produce false "module not found" errors even when the file is correct. Fix: restart the dev server, and in stubborn cases delete `.next` first — not a code bug.
- **Cascading TypeScript errors usually mean one structural issue near the first error**, not many separate bugs. Check the earliest reported location in the raw file directly before trusting the full error list.
- **`next/image`'s optimizer was unreliable in this environment** (persistent broken/blank thumbnails, never fully root-caused). Working fix where it's still used: `unoptimized` + explicit `width`/`height` (not `fill`). Most of the app has since moved to plain `<img>` tags specifically to avoid re-triggering this — don't reintroduce `next/image` broadly without cause.
- **A plain `<a href>`, even wrapped in `motion.a`, forces a full page reload** — Motion's wrapper doesn't grant client-side routing. Use `next/link`'s `<Link>`, or manual `pushState` + `preventDefault()`.
- **`react-hooks/refs` lint rule** flags reading `ref.current.getBoundingClientRect()` directly in a render body — do it inside an effect or event handler and store the result in state.
- **`react-hooks/set-state-in-effect` lint rule**, plus a related real bug: calling one `setState` nested inside a *different* `setState`'s functional-updater callback produced an actual React warning. Keep state updates as plain sequential calls, not nested inside another updater. (This rule is currently failing lint at `app/page.tsx:36` — see `PROJECT_CONTEXT.md`.)
- **Motion (`motion/react` 13.x) wraps every `ref` in its own stable internal callback** (see `use-motion-ref.mjs`), which React only invokes when the underlying DOM node actually mounts/unmounts — *not* just because the `ref` prop's value changes between renders. A conditional ref like `ref={isSelected ? myRef : undefined}` on a `motion.*` element will silently never fire again once the element has mounted once with `ref=undefined` (e.g. every grid tile mounts before anything is ever selected) — Motion has no way to know your prop "changed" since its own wrapper callback's identity didn't change, so React never re-attaches. Symptom: `ref.current` (or a `useLayoutEffect` reading it) stays `null` forever, with zero console errors. Fix: attach the ref *unconditionally* (e.g. into a `Map` keyed by id, populated once at true mount for every instance), then look values up from that map later instead of relying on a ref being (re)attached on demand.
- **`layoutId` on a *persisting* element (same DOM node, never unmounts) does not reliably animate its own size changes**, even with `layoutId` made unconditional (present from true first mount) and an explicit `transition` prop. Verified empirically (in-browser `requestAnimationFrame` polling of `getComputedStyle`, not just eyeballing it — repeated round-trip-based sampling via Playwright is too imprecise for sub-second animation timing, gives misleadingly-instant-looking readings): the CSS class change (e.g. a bigger `max-width`/`max-height` on `isSelected`) applies instantly, and any `transform` Motion adds is a barely-visible wobble (scale staying within ~0.99–1.0), not the expected FLIP-style interpolation — regardless of the `transition` duration passed (tested up to 5s with zero difference). `layoutId` *does* correctly animate the cross-component case (this element unmounting while a *different* element with the same `layoutId` mounts elsewhere, e.g. cover→hero on focus) — that's a separately-verified, working mechanism, don't conflate the two. For an in-place resize of a persisting element, skip `layoutId`/Motion entirely and use a plain CSS `transition` on the specific properties that change (e.g. `transition-[max-width,max-height] duration-[600ms]`) — reliable, simple, and doesn't fight with whatever `layoutId` is doing for the *other* transition this same element may also participate in.
- **Follow-on trap from the above: a CSS `transition` on a layout property (`max-width`/`max-height`/etc.) is not synchronous, so anything that measures the element via `getBoundingClientRect()` right after the class change (e.g. a `useLayoutEffect` keyed on the triggering state) captures a size from partway through — sometimes not even a sane midpoint, but an odd early transient (observed: briefly *smaller* than either the start or end size around ~15% into the transition).** Anything whose own layout depends on that measurement (e.g. sibling elements sized off the growing element's height) will silently lock onto that wrong value and never self-correct, since nothing re-triggers the measurement once the transition actually finishes. Fix: also listen for `onTransitionEnd` on the animating element (checking `e.propertyName` for the specific property you care about) and re-measure there, in addition to — not instead of — the immediate measurement, so there's still a reasonable value available right away (needed for e.g. deep-linking straight into a state where nothing is actually transitioning) but it gets corrected once the real layout settles.
- **`scrollWidth`/`clientWidth` (or any size read) on a container of unloaded `<img>`/`<video>` elements is unreliable even from a `useLayoutEffect` that fires strictly after the container mounts** — confirmed by direct testing (an in-browser debug log showing the read value on both the initial and a deliberately-gated later re-render). An `<img>` with no `width` attribute and an unresolved `src` hasn't established its intrinsic size yet, so a `width:auto`-sized image can report a much smaller box than its eventual loaded size, making a genuinely-overflowing flex row measure as "fits fine." Gating the read on a later render (e.g. via a "not measured yet" `null` state) does *not* fix this on its own — the problem isn't *when* React re-renders, it's that the images themselves haven't loaded yet at that point either.
  - A synchronous estimate (item count × expected size, no real measurement) was tried first as a simpler alternative and **was wrong often enough in practice to matter** — two projects with the *same* supporting-image count (`ann-mukcyen-styling` and `one-or-eight-x-kamiya`, both 9) had different real overflow outcomes purely from differing aspect ratios, which a count-based guess structurally cannot see. Don't reach for this shortcut for anything where getting it wrong is visible/reintroduces a real bug, only for cases where "close enough" truly doesn't matter.
  - A proper fix along these lines (wait for real `load`/`error` events on the gallery's `<img>` elements, capped at a 400ms timeout, deliberately never waiting on `<video>` since some of these files are 100MB+) was built and verified correct — including on the exact `ann-mukcyen-styling`/`one-or-eight-x-kamiya` case that exposed the estimate as wrong. **The user then explicitly simplified the requirement anyway**, same day: always animate from whichever end is next to the key image, full stop, even on a gallery large enough to overflow (accepting that the first images to animate can be off-screen until scrolled to, rather than trying to detect and special-case that). `galleryStaggerForward` in `components/PortfolioGallery.tsx` is now just `expandRight` — no measurement, no async loading, no gating, nothing left of any of the approaches above. Don't reintroduce overflow-detection for this without being asked again; if it comes up, this whole history (three attempts, the count-based one demonstrably wrong, the load-based one correct-but-unwanted) is worth reading first.

## Rejected approaches — do not reintroduce

- Real page navigation (separate `/work/[slug]` route reached via normal link clicks) as the primary click-through experience — always felt like "a new page," the explicit thing being avoided from the start.
- React's native View Transitions API (`<ViewTransition name=...>`) for a shared-element morph across a route navigation — implemented correctly per docs, compiled cleanly, but never visibly animated, cause undiagnosed. Replaced by Motion's `layoutId` within a single component tree. Don't re-suggest View Transitions as "the fix" without knowing this was already tried.
- A full-screen overlay that grew the clicked image into a larger box *repositioned elsewhere* on screen (`ExpandedProject.tsx`, since deleted) — the key image must stay in the same spot (same grid cell/center point) it had in the grid.
- The cover resizing at all on click (tried 2026-08-16, reverted same day — see "Confirmed interaction model" history note) — the cover is pixel-identical, full stop, whether or not it also gets shown enlarged elsewhere via the carousel/big-image mechanism.
- A separate "focused" step (vertical sidebar + big hero, reached via a second click, with the carousel hiding/relocating to make room) — tried, worked, then superseded 2026-08-16 by the current always-visible-carousel-with-swap-in-place model because the relocation itself felt like too many steps. Also retired along with it: the Motion `layoutId` shared-element system for this whole component (grid-cover↔hero and thumbnail↔hero FLIP animations) — with nothing left that morphs between two different mounted locations, `layoutId` had no remaining purpose and was removed. Don't reintroduce `layoutId` here without a concrete reason tied to an actual cross-location morph.
- Filtering that removes non-matching projects from the rendered array — caused reflow/renumbering. Replaced with opacity/pointer-events toggling on a permanently-rendered full list.
- Computing thumbnail size by dividing available space by row/column count to force everything onto one screen — produced oversized, inelegant thumbnails. Whitespace should come from generously-sized cells, not images stretching to fill them.
- A single shared gap constant for both the description offset and the image-to-image gallery offset — produced a visibly inconsistent gap. Use separate constants (smaller for image-to-image, larger for the description).
- Treating the overview grid's number + thumbnail as one flex-centered unit (either centered together in the cell, or the number tightly wrapped around just the thumbnail so it tracks the thumbnail's position/size) — went through several iterations of this shape before landing on the current spec (see "Grid target spec" above): the number and thumbnail are two *independently* positioned elements within a shared large cell, not a stack. Also previously rejected specifically: the row-track height shrinking to fit exactly one viewport (`minmax(0,1fr)` rows sized to `100vh - header`) — replaced by fixed 300px rows with page-level scroll for additional rows.
